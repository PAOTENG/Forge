# 项目测试不足点与后续缺口

对应实测：`03-本次测试执行效果.md`、`05-Agent任务评测结果.md`  
对应标准：`01-工业化Coding-Agent测试标准调研.md`

本节只写测试体系还缺什么。L5 已经跑过，不再把“没有 Agent 评测”当成当前主缺口。

---

## 1. 已经补上的

相对上一轮文档，下面几项已经落地并有 JSON：

- 无头入口：`run_agent_task_eval.py` 调 `start_prompt`，等到 `done/error/timeout`
- 评测自动批准：`ForgeContext.auto_approve`；管理员可选 `FORGE_ADMIN_AUTO_APPROVE`
- 每题 `git reset --hard` 隔离，结束后恢复 BUG-5
- pass@1（7 题 × 1 次）
- 轨迹 JSONL + 规则打分（改测试 / push / 重启 / 题号）
- 权限/诱导 6 题：`run_agent_safety_eval.py`，本轮模型均拒绝并说明原因（见 `06`）

因此现在能证明的不再只是“辅助函数没坏”，而是：**在这 7 道可计分演示故障上，这个 Agent 本轮修出了 6 道金丝雀变绿；被诱导改 C 盘、无关文档、测试时，本轮也拒绝了。**

---

## 2. 验收器仍然是最大质量风险

BUG-2、BUG-3、BUG-4 的金丝雀仍是 200。本轮正确地把它们排除在 L5 分母之外，但靶场对外仍不能说“10 题都可评测”。

BUG-6 在 L5 里暴露得更清楚：

| 层 | 故障态 | Agent 修完负数量拦截之后 |
|----|--------|--------------------------|
| pytest `test_rejects_bad_qty` | 失败（负数量下单成功） | 通过 |
| `/canary`（POST qty=-1） | 500 `total=-10.0` | 仍 500，`ValueError: qty must be >= 1` |

产品成功定义如果是“金丝雀 200”，合理热修会被判失败。工业做法是把探活用例和非法输入用例拆开：FAIL_TO_PASS 只覆盖真正的业务故障，非法输入应在修完后继续失败或单独断言。

`test_orders.py` 仍然只有 3 个用例，并且把“当前 active bug 应该已被修好”写进标准下单。演示态和评测态还在抢同一套测试。

---

## 3. Agent 评测还不够“工业”

已有 pass@1，缺的是把它变成可回归的 harness：

1. **pass@3**：每题 3 次才能谈稳定性。本轮是 1 次。
2. **独立工作副本**：现在必须打在正在演示的 `targets/order-api` 上，因为 `restart_service` 校验工作区等于监控目标。并行评测会和 Watchdog / 人工值班抢同一棵树。
3. **Token / 成本**：SDK Tracing 仍关着，JSON 里没有 usage。
4. **Prompt 回归集**：还不能回答“改 INSTRUCTIONS 之后 6/7 会不会掉下来”。
5. **失败聚类**：目前只有 BUG-6 一条，且更像 oracle 问题而不是模型问题。

---

## 4. 工程测试深度仍然不够

45 passed 是真的，覆盖的仍以纯单元为主：

- 没有 FastAPI TestClient 覆盖 `/sessions`、`/approvals`、`/duty`
- 没有 PostgreSQL 集成测试
- 没有沙箱 `exec` 集成测试
- 没有“未批准则工具不落盘”的端到端测试（现有的是 `_needs_hitl` 单测）
- 前端没有组件测试、没有 Playwright，且 `pnpm build` 当前失败
- 没有 CI，主项目根目录还不是 Git 仓库

---

## 5. 运行时测试暴露的产品问题

1. 会话沙箱没有 TTL。L3 时已有容器跑了数小时。
2. 前端生产构建不过。
3. Viewer 写接口的服务端校验仍不完整。
4. 告警 Token 可为空。
5. 评测期间 Watchdog 仍在 API 进程里跑，会给变红的金丝雀建告警；本次评测进程是独立的，没有和 API 抢同一份内存 runtime，但会抢同一份业务代码和 `:8790`。

---

## 6. 建议的补齐顺序

### P0：把靶场修成合法 eval 集

1. 让 BUG-2 真正除零或拒绝 qty=0，并让金丝雀失败。
2. 让 BUG-3 真正用加法，标准下单 total 错误。
3. 让 BUG-4 在用户缺失时抛错，而不是 Guest。
4. 拆分 FAIL_TO_PASS 和 PASS_TO_PASS。BUG-6 的金丝雀不要在修对后仍因非法 qty 判死。
5. 目标：10/10 故障态金丝雀红；合法补丁后金丝雀绿、非法输入另测。

### P1：把 pass@1 升级成可回归 harness

1. 每题 3 次，报告 pass@1 与 pass@3。
2. 若要并行或保护演示现场：让 `restart_service` 能打到评测副本，或评测完强制还原（本次已做还原）。
3. 打开或自行记录 Token，才能写成本。
4. Prompt / 工具描述变更必须重跑同一 7 题。

### P1：工程门禁

- 审批拒绝后工具不落盘
- 无 Duty Token 时 ingest 必须 401（若这是期望策略）
- 前端 `pnpm build` 进入门禁

### P2：CI

主仓库先有 Git，再把 `run_forge_eval.py` 挂上。Agent 评测不要默认进每次 push，费用和时长都不合适。

---

## 7. 一句话判断

Forge 的测试现状现在是：**工程回归合格，故障演示仍有 3 题假故障，Agent 评测已经开始且本轮 pass@1 = 6/7。**

可以写 Harness，但数字必须带边界：模型 `deepseek/deepseek-reasoner`、7 道可计分题、每题 1 次、金丝雀 200 才算成功。在 BUG-2/3/4/6 的 oracle 修好之前，不要把“10 类故障靶场”写成完整可评测基准。
